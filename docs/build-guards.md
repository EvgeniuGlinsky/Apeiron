# Предохранители сборки

Документ о том, почему сборка однажды выдала негодный APK и отрапортовала
успехом, и что теперь этого не даёт повторить.

## Что случилось

23 сентября 2026 года `flutter build apk --release` завершилась успехом и
выдала APK **без `librust_lib_apeiron.so`**. Приложение упало бы на запуске:
без этой библиотеки нет ни ключей, ни личности — ядро целиком живёт в Rust.

В выводе была ровно одна строка, говорящая о беде:

```
SEVERE: rustup not found in PATH.
```

и следом — `√ Built build\app\outputs\flutter-apk\app-release.apk (44.4MB)`.

Поймано случайно, при ручном просмотре содержимого APK перед выдачей.

## Почему так вышло

Причин оказалось две, независимых.

### 1. Окружение не дошло до сборки

`CARGO_HOME`, `RUSTUP_HOME` и путь к `cargo/bin` заданы на уровне пользователя
правильно. Но терминал, из которого шла сборка, был запущен **раньше**, чем эти
переменные появились, и унаследовал окружение без них. Демон Gradle, поднятый
из этого терминала, получил то же пустое окружение и держит его до перезапуска:
задать переменные в сессии уже после старта демона недостаточно.

Cargokit ищет `rustup` только в `CARGO_HOME/bin`, `%USERPROFILE%\.cargo\bin` и
по `PATH`. Задать путь к нему свойством Gradle или через `cargokit.yaml` нельзя
— такой настройки в cargokit нет, это проверено по его исходникам.

### 2. Батник глотал код возврата

Это главное и куда неприятнее первого.

Cargokit, не найдя rustup, честно печатает `SEVERE` и завершается с кодом 1.
Gradle вызывает его через `execOperations.exec {}` без `ignoreExitValue`, то
есть **обязан** упасть. Не падал.

Виноват `cargokit/run_build_tool.cmd`. Он заканчивался так:

```bat
"%DART%" "%PRECOMPILED%" %*

REM 253 means invalid snapshot version.
If %ERRORLEVEL% equ 253 (
    ...
)
```

Последний исполненный оператор — `If` с ложным условием. Сам по себе он
успешен, и его успех становится кодом возврата всего файла. Ошибка `dart`
теряется бесследно.

Проверено отдельным опытом на трёх вариантах батника:

| Батник | Код возврата |
|---|---|
| `cmd /c exit 1` и всё | 1 — верно |
| то же плюс `If %ERRORLEVEL% equ 253 (...)` в конце | **0 — ошибка потеряна** |
| то же плюс `exit /b %ERRORLEVEL%` | 1 — верно |

Это баг cargokit на Windows, не особенность машины. Под macOS и Linux его нет:
`run_build_tool.sh` начинается с `set -e`.

Под Windows-десктоп дыры тоже нет, но по другой причине: `cargokit.cmake`
объявляет `.dll` как `OUTPUT` кастомной команды, и без файла цель просто не
считается собранной.

## Что теперь стоит

### Правка в cargokit

В конец `app/rust_builder/cargokit/run_build_tool.cmd` добавлено
`exit /b %ERRORLEVEL%` с комментарием `APEIRON PATCH`.

**Это вендорный файл.** Обновление `flutter_rust_bridge` или cargokit его
перезапишет, и правка исчезнет молча. Поэтому она не единственная.

### Предохранитель в нашем Gradle

`app/android/app/build.gradle.kts`, две задачи:

* **`checkRustToolchain`** — до начала компиляции проверяет, что `rustup` вообще
  виден, теми же правилами поиска, что у cargokit. Падает за секунды с рецептом
  вместо двух минут компиляции и сообщения «Maybe you need to install Rust?»,
  которое уводит в сторону: Rust на машине стоит, его не видно сборке.
  Привязана к `preBuild`.
* **`verifyRustLib<Вариант>`** — после упаковки открывает **готовый APK** и
  требует, чтобы для каждой упакованной архитектуры в нём лежала
  `librust_lib_apeiron.so`. Список архитектур не задан заранее: он зависит от
  того, как вызвана сборка (`--target-platform`, `--split-per-abi`), поэтому
  проверяется то, что реально попало внутрь. Привязана к `assemble<Вариант>` —
  то есть к тому, что вызывает `flutter build apk`.

Обе живут в нашем файле и переживут обновление cargokit.

### Верификатор готового файла

`app/tool/verify_apk.dart` — отдельная программа, которой всё равно, кто и как
собрал APK:

```bash
cd app && dart run tool/verify_apk.dart build/app/outputs/flutter-apk/app-release.apk
```

Проверяет: библиотеку Rust для каждой архитектуры, движок Flutter, наличие
блока подписи, манифест, байт-код, таблицу ресурсов, опись ресурсов Flutter и
**три вшитые гарнитуры поимённо** (Inter, Syne, JetBrains Mono NL) — потому что
`google_fonts` использовать нельзя и отсутствие шрифта внутри APK означает, что
текст поедет системным.

Zip читается своим кодом (`app/tool/apk_report.dart`): нужны только имена
записей, распаковка не требуется вовсе. Тянуть ради этого зависимость в проект,
который обещает проверяемость, — плохой размен.

**Прогонять перед каждой выдачей APK наружу.** Код возврата: 0 — годен,
1 — негоден, 2 — нечего проверять.

### Остальное

* `rust-toolchain.toml` — фиксирует цели Android и компоненты (`rustfmt`,
  `clippy`). Без целей cargokit соберёт пустоту.
* Строгие линты распространены на мост `app/rust`: `unwrap`, `expect`, `panic`
  запрещены — это код на границе FFI, где паника роняет процесс целиком.
  `unsafe_code = "deny"` (а не `forbid`, как в ядре) с единственным снятием на
  объявлении `mod frb_generated`: FFI без `unsafe` не бывает, а `forbid` нельзя
  снять даже осознанно.
* `.github/workflows/checks.yml` — формат, линты с `-D warnings`, тесты Rust,
  `cargo deny check`, анализ и тесты Flutter. Чужие действия закреплены **по
  SHA, а не по тегу**: тег в чужом репозитории переставляется, SHA — нет.
* `deny.toml` — белый список лицензий и запрет отозванных версий.

## Как проверялось, что предохранители работают

Предохранитель, который ни разу не срабатывал, предохранителем не является.
Каждый проверен намеренной поломкой:

| Ломаем | Ожидание | Что вышло |
|---|---|---|
| убрать `rustup` из окружения | падение до компиляции | `checkRustToolchain` уронил сборку за 2 с с рецептом |
| подменить имя искомой библиотеки | падение на готовом APK | `verifyRustLibDebug` уронил сборку, назвав все три архитектуры |
| вызвать cargokit без окружения | Gradle видит ненулевой код | `finished with non-zero exit value 3`, сборка упала |
| APK без библиотеки Rust | верификатор заворачивает | тесты `test/apk_report_test.dart`, 9 проверок |

## Чего эти предохранители не ловят

Честно, чтобы не было ложного спокойствия:

* **Устаревшую библиотеку.** Если cargokit не запустился, а `.so` от прошлой
  удачной сборки осталась в промежуточных каталогах, APK соберётся с ней, и
  проверка на наличие пройдёт. Именно так уцелел отладочный APK в тот день.
  Закрывает это не проверка наличия, а правка батника: теперь падение cargokit
  роняет сборку и до упаковки дело не доходит.
* **Подмену содержимого библиотеки.** Проверяется наличие файла, не его
  происхождение. Против этого работает воспроизводимость сборки, а её у нас
  пока нет.
* **AAB.** Проверяется APK. Когда дойдёт до публикации в магазине, проверку
  надо будет распространить на `SingleArtifact.BUNDLE`.
